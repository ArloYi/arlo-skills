# 本地完整修改日志

使用项目档案中的 `release.log_file` 作为唯一修改日志，默认可设为 `docs/RELEASES.md`。日志跟随源代码提交到 GitHub，不包含凭证或仅适合本机保存的信息。

## 推荐结构

```markdown
# <产品名称>完整修改日志

## 记录范围
- 起始时间
- 当前时间
- Git 提交数量
- 正式上线次数
- 当前版本
- 线上地址
- 当前生产代码
- 当前发布记录
- 当前回滚版本

## 当前完整功能
### 1. <功能模块>
- 当前真实可用能力

## 完整迭代时间线
### <版本或日期>，<版本主题>
代码：`commit-sha`
- 本版具体改动
- 回滚点：`previous-version`

## Git 提交索引
| 日期 | 提交 | 类型 | 内容 |
| --- | --- | --- | --- |

## 当前仍未开放的功能
- 已明确但尚未交付的能力；没有时写“无”
```

## 维护规则

- “记录范围”反映当前生产事实；生产代码与纯日志提交分别记录，不能混为一个 SHA。
- “当前完整功能”按产品自然模块分类，是当前真实可用能力的完整目录，不是本版新增功能清单。
- “完整迭代时间线”按时间顺序保存每版主题、代码 SHA、具体改动和回滚点。
- “Git 提交索引”从真实 Git 历史生成，区分功能、修复、文档或发布记录，不编造提交。
- “当前仍未开放的功能”只收录项目文档、任务或用户明确确认的计划，不根据想象补充路线图。
- 只在新版本完成部署并通过线上验证后新增正式版本块；开发过程中的每次修改、未上线提交和普通文档调整不单独写版本日志。
- 已上线版本随后发生回滚时，更新同一个版本块的状态和回滚结果，不另造一个从未上线的版本。
- 纯日志提交不触发重复部署；下一次维护日志时再更新“当前发布记录”，避免为了记录自身 SHA 形成递归提交。
- 旧日志不必一次性重写；首次接入时根据可验证历史尽量补齐，无法确认的旧事实明确省略。
