# 网站发布管家

把网站上线处理成一条清楚、可继续、可验证的流程：

```text
整理本地文件和文档 → 检查与构建 → GitHub 留存 → 部署接入或更新 → 线上验证 → 发布记录
```

只固定流程和安全边界，不固定云厂商、服务器目录、框架或部署工具。

## 先判断是哪种任务

- **首次上线**：项目还没有 GitHub 仓库、部署目标或正式域名；执行完整接入。
- **日常更新**：仓库和部署方式已经存在；沿用项目档案直接发布新版本。
- **部分操作**：“只同步 GitHub”“只部署”“检查状态”“回滚”时只执行指定部分。

未指定网站时使用当前 Git 根目录；用户指定名称时，可从本机注册表解析：

```bash
python3 <skill-dir>/scripts/release_manager.py resolve "<网站名称或别名>"
```

项目目录、档案和用户所指网站冲突时停止确认，禁止跨项目操作。

## 展示进度和预计时间

开始执行时，根据实际范围列出阶段、当前进度和预计总用时；部分操作只显示相关阶段。使用紧凑格式，例如：

```text
[■■■□□□] 3/6 GitHub 留存｜已完成 50%｜预计剩余 4–8 分钟
```

- 进入新阶段或完成关键节点时更新一次。
- 长时间未进入下一阶段时，主动说明正在处理什么、是否正常以及最新预计剩余时间；频率根据任务耗时和用户要求调整。
- 构建、网络、平台队列或人工授权改变耗时后立即重新估算；使用时间区间，不制造精确承诺。
- 等待用户授权时明确标为“等待确认”，把等待时间与主动执行时间分开。
- 遇到失败或阻塞时显示停在哪一步、已完成内容和安全的继续入口。

进度是沟通摘要，不建立额外服务或复杂状态系统。以实际验证结果决定阶段是否完成，不能只按已运行命令数量计算百分比。

## 安全边界

1. 先读取项目规则、README、部署文档、Git 状态和现有脚本。
2. 保留用户改动，不删除或提交归属不明的文件。
3. 发布到公开仓库的内容必须是经过筛选、泛化和脱敏的公开副本，不把本机 Skill 或项目目录原样镜像上传。
4. GitHub 推送前检查 staged diff、待推送文件和 Git 历史；身份信息、个人偏好、真实项目与基础设施数据、凭证或无法判断归属的内容必须留在本地。
5. 检查、构建、push 或线上验证失败时停止，并保留当前进度以便继续。
6. 仓库公开性、DNS、证书、服务器权限、数据库、付费资源、强制推送和破坏性操作必须单独确认。

## 首次上线

### 1. 整理本地项目

- 盘点源码、文档、素材、生成物、缓存和临时文件。
- 更新 README、使用说明和部署说明；正式版本日志在上线验证成功后统一维护。
- 补齐 ignore 规则，排除凭证、缓存和无需留存的构建文件。
- 不擅自删除疑似残留；无法判断时列出并询问。

### 2. 检查并构建

- 识别项目技术栈和实际入口。
- 运行项目已有的检查、测试和生产构建命令。
- 确认可部署产物或平台原生构建入口。

不要凭空发明构建命令。必需检查失败时不得继续发布。

### 3. 建立 GitHub 留存

使用 GitHub CLI 检查登录账号和仓库状态：

- 已有关联仓库：核对 remote、分支和仓库归属。
- 没有仓库：确认仓库名称及公开或私有后，通过 `gh repo create` 创建并关联。
- 初始化 Git 时，只纳入源码、必要文档、项目配置和版本日志。
- 提交并 push；后续部署只使用已经推送成功的 commit SHA。

GitHub 默认保存可继续开发的源代码。构建产物只在项目部署方式或仓库规则明确要求时提交。

仓库为公开状态时，推送前必须阅读并执行 [references/public-export.md](references/public-export.md)。公开版是有意维护的发布副本：删除只服务于某个人的习惯和上下文；将确有通用价值的规则改写成不指向个人、项目或供应商的表达；所有示例使用占位符或保留示例值。脱敏未完成时不得 push。

### 4. 接入部署并上线

- 已有部署目标时沿用项目权威文档和已验证方法。
- 没有部署目标时，根据项目类型和用户现有资源选择服务器、托管平台、CI/CD、容器或对象存储。
- 首次接入时记录执行入口、部署目标、产物、验证地址和恢复方式。
- 需要域名和 HTTPS 时，确认目标后完成 DNS、绑定和证书配置。

具体选择原则见 [references/deployment-guidance.md](references/deployment-guidance.md)。不得为了统一格式强制迁移平台、目录或工具。

### 5. 验证并记录

- 验证正式地址、HTTPS、关键页面和核心功能。
- 能提供版本标记时，核对线上版本和 commit SHA。
- 新版本完成部署并验证成功后，统一维护一次本地更新日志：刷新生产快照、当前完整功能、未开发功能和 Git 索引，并写入本版逐项改动、时间、生产 SHA、验证结果和回滚点。
- 把最终日志推送到 GitHub；纯记录提交不重复部署。

本地更新日志默认使用档案中的 `release.log_file`。它只在一个新版本实际上线或上线后发生回滚时统一维护；开发过程中的零散修改、未上线提交和普通文档调整不单独记版本日志。每个版本只追加或更新自己的历史块，不覆盖其他版本。格式见 [references/release-log.md](references/release-log.md)。

## 日常更新

已有项目档案时执行简化链路：

```text
整理文件和文档
→ 检查与构建
→ 确定版本和本次发布内容
→ commit / push
→ 按档案部署该 commit
→ 线上验证
→ 统一维护版本日志并保存最终记录
```

常用辅助命令：

```bash
python3 <skill-dir>/scripts/release_manager.py preflight --project <项目根目录> --run-checks
python3 <skill-dir>/scripts/release_manager.py next-version --project <项目根目录>
python3 <skill-dir>/scripts/release_manager.py verify-remote --project <项目根目录> --version <版本号> --commit <提交SHA>
python3 <skill-dir>/scripts/release_manager.py record --project <项目根目录> --status success --version <版本号> --commit <提交SHA> --rollback <回滚点> --change "<本版改动>"
```

项目档案只保存执行所需的非敏感事实，规范见 [references/release-profile.md](references/release-profile.md)。没有档案时自动发现并建立，不要求用户手工填写整份 JSON。

## 完成标准

只有以下条件全部满足，才宣布“上线成功”：

- 本地文件和文档已整理；
- 必需检查和构建通过；
- 对应源代码已推送到 GitHub；
- 公开仓库的待推送内容已完成泛化、脱敏和 staged 内容检查；
- 网站已部署到明确环境；
- 正式地址和核心功能验证通过；
- 本地更新日志已保存完整功能、未开发功能、版本改动、生产 SHA 和回滚点。

最终只汇报网站、版本、线上地址、更新摘要、commit SHA、验证结果和回滚点。
